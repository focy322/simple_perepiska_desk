# Инструкции для работы с проектом

## Проект и структура

Vent — настольный мессенджер на C++20 и Qt 6 Widgets. Сборка использует CMake и MinGW; цель приложения — `vent`. Для хранения учётных данных подключён qtkeychain через FetchContent.

- `src/main.cpp` — запуск приложения и обработка единственного экземпляра.
- `src/mainwindow.cpp`, `src/mainwindow.h`, `src/mainwindow.ui` — главное окно, компоновка и взаимодействие с UI.
- `src/controllers/` — связь интерфейса с сервисами и обработка результатов запросов.
- `src/services/` — HTTP/WebSocket-запросы и работа с сервером без зависимости от виджетов.
- `src/models/` — модели списков чатов, сообщений и поиска.
- `src/delegates/` — отрисовка элементов списков.
- `src/widgets/` — собственные виджеты, окна и диалоги.
- `src/requests/` — состояния запросов, повторные попытки и обработка ошибок.
- `src/utils/` — общие структуры данных, утилиты, пути и адреса API.
- `resources/` — QSS, иконки, изображения, звуки и ресурсы Windows.

## Оформление и ресурсы Qt

- Храни весь QSS в `resources/styles/`. Не добавляй строки с QSS в C++ или свойства `styleSheet` в `.ui`.
- Основной стиль — `resources/styles/main.qss`. Главное окно загружает его из `:/styles/main.qss`; дочерние виджеты наследуют оформление.
- Шаблон анимации кнопки входа — `resources/styles/login-button-animation.qss`: `%1` обозначает цвет фона, `%2` — цвет текста. В C++ допустимы загрузка шаблона, подстановка значений и сброс временного стиля.
- Общие операции со стилями находятся в `src/utils/stylehelper.h` и `.cpp`, в пространстве имён `StyleHelper`: `load` загружает QSS из ресурса, `repolish` обновляет оформление виджета.
- Для адресных правил задавай виджетам устойчивые `objectName`. Для состояний используй свойства и селекторы QSS; после изменения динамического свойства вызывай `StyleHelper::repolish`, как в `setAuthStatus`.
- Новые QSS, иконки и другие встроенные файлы регистрируй в `resources/resources.qrc`. Обращайся к ним через пути `:/...`, без зависимости от рабочей директории или внешних файлов рядом с `.exe`.
- В `.ui` оставляй структуру формы, компоновку и обычные свойства виджетов. При переносе стилей сохраняй остальные свойства и вложенность XML.
- При изменении селекторов учитывай приоритет правил и область их действия: фон, прозрачность, рамки и состояния `hover`, `pressed`, `disabled`, `focus` должны сохранять ожидаемое поведение.
- Пользовательская отрисовка через `QPainter` находится в виджетах и делегатах; её изменение рассматривай отдельно от переноса QSS.

## Правила изменения кода

- Следуй стилю окружающего кода: отступы в четыре пробела, существующие соглашения об именах и расположении скобок.
- Сохраняй UTF-8 и текущие окончания строк. Пользовательские тексты и существующие комментарии преимущественно на русском.
- Размещай новую логику в подходящем компоненте. Сетевые операции добавляй в сервисы, данные списков — в модели, отрисовку элементов — в делегаты.
- Для взаимодействия компонентов используй сигналы и слоты Qt. Учитывай время жизни `QObject`, родительское владение и контекст подключения лямбд.
- Сохраняй асинхронное выполнение сетевых операций; не блокируй поток интерфейса.
- Адреса API находятся в `src/utils/endpoints.h`, общие структуры ответа — в `src/utils/parsed_objects.h` и `.cpp`.
- Учитывай ветки `Q_OS_WIN`, `Q_OS_LINUX` и `QT_DEBUG`, если изменение затрагивает платформенное поведение или различия Debug/Release.
- Перед правками проверяй `git status` и нужные участки кода. Сохраняй существующие изменения пользователя и ограничивай правки текущей задачей.
- Не редактируй сгенерированные `ui_*.h`, `moc_*.cpp`, `qrc_*.cpp`, содержимое `_deps/`, каталогов сборки и `dist/` как исходники проекта. Временные проверочные файлы можно создавать в каталоге сборки.

## Сборка

Сначала используй существующую конфигурацию, если она доступна:

```powershell
cmake --build cmake-build-debug --target vent --parallel 4
```

Для Release:

```powershell
cmake --build cmake-build-release --target vent --parallel 4
```

Если нужна новая конфигурация, проверь установленные CMake, Ninja, MinGW и Qt. Пример команды; путь к Qt замени на фактический:

```powershell
cmake -S . -B cmake-build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_PREFIX_PATH="<путь к Qt 6/mingw_64>"
```

- Компилятор MinGW и библиотеки Qt должны быть совместимы. Пути к инструментам уже настроенной сборки можно посмотреть в её `CMakeCache.txt`.
- Требуемые модули Qt перечислены в `CMakeLists.txt`: Core, Gui, Network, WebSockets, Multimedia, MultimediaWidgets и Widgets.
- При первой конфигурации FetchContent скачивает qtkeychain версии `0.14.2`; для этого нужен доступ к сети.
- CMake автоматически находит `.cpp`, `.h`, `.ui` в `src/` и `.qrc` в `resources/`. Для включения нового QSS достаточно добавить его в `.qrc`.
- Не меняй настройки сборки и упаковки для обхода локальных проблем с путями к инструментам.

## Проверка результата

- Для изменений исходников, `.ui` и ресурсов собери цель `vent` в затронутой конфигурации. Для правок только документации пересборка не нужна.
- В репозитории пока нет отдельного постоянного набора тестов приложения. Проверяй затронутые сценарии, а при исправлении ошибок добавляй осмысленные проверки, если они оправданы изменением.
- При изменении оформления проверь соответствующие экраны, состояния кнопок, фокус полей и динамически создаваемые виджеты. Для переноса стилей без изменения дизайна полезно сравнение отрисовки до и после.
- Различай автономную проверку UI и проверку с сервером: Debug-конфигурация также использует удалённый сервер из `endpoints.h`. Для проверки только оформления предпочитай автономный запуск без сетевых действий.
- Перед завершением просматривай diff и проверяй новые строки на ошибки форматирования с учётом CRLF: `git -c core.whitespace=cr-at-eol diff --check`.
- В ответе кратко указывай, что изменено, что проверено и какие проверки не удалось выполнить.
